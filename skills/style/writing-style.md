# 문체 스타일 가이드 (writing-style)

모든 산출물에 적용하는 표현 층위 규칙. 템플릿이 "어떤 섹션을 어떤 순서로"를 정한다면,
이 가이드는 "문장을 어떻게 쓰나"를 정한다. **작성자는 초안 전에 정독하고, 가독성 리뷰어는
아래 규칙 위반을 반려 사유로 삼는다** (리뷰어용 판정 목록은 `review-checklist.md` 참조).
목표 문체: 간결한 실무체 — 동료에게 공유하기 위한 문서라는 전제를 항상 깔고 쓴다.
문서 유형(학습·문제 해결·참조·설명)별 요건은 `doc-types.md`가 정한다.

절 제목 옆 괄호는 근거가 된 토스 테크니컬 라이팅 가이드 원문 파일이다(`docs/` 기준 경로,
출처는 문서 끝 참조).

## 1. 최종 상태만, flat하게 (최우선 규칙)

문서는 작업의 연대기가 아니라 결론의 전달이다. "처음엔 A로 했다가 → 문제를 발견해서 →
B로 바꿨고 → 최종적으로는" 같은 과정 서술을 본문 논리 구조로 쓰지 않는다. 서술 순서는
시간순이 아니라 최종 내용 기준으로 짠다: **지금 무엇인가 → 왜 그런가.**

과정·시행착오 trace가 독자에게 실제로 중요한 경우(실험 리포트의 실패 기록, 검토했으나
기각한 대안 등)에만 별도 섹션("검토한 대안", "시행착오" 등)으로 격리해서 담고, 본문
서술에 섞지 않는다. 검토한 대안은 `대안 | 택하지 않은 이유` 표가 기본이다.

## 2. 독자 상정

독자는 동료다 — 팀·레포의 일반 맥락은 알지만, 이 문서가 다루는 변경·논의·실험은 모른다.
모든 용어 선택과 배경 설명의 깊이는 이 독자를 기준으로 정한다.

## 3. 개요는 가치를 먼저 (`architecture/overview.mdx`, `architecture/value-first-cost-later.mdx`)

요약/개요 섹션은 "이 문서를 읽으면 무엇을 알게 되거나 할 수 있게 되는가"에 먼저 답한다.
배경 지식, 도입 경위, 일반론은 그다음이다. 독자는 개요만 읽고 이 문서가 자기 문제와
관련 있는지 판단한다. 개요는 제목 바로 아래, 본문보다 앞에 둔다.

- Don't: "이 문서는 재시도 로직의 도입 배경과 구현을 소개합니다. 재시도란…"
- Do: "이 문서를 읽으면 API 요청 실패 시 자동 재시도를 어떻게 붙이는지 알 수 있다."

독자가 얻을 것(예: "이 기록으로 답할 수 있는 질문" 목록)은 문서 끝이 아니라 앞쪽에
둔다. 세부 설정·부가 정보는 그 뒤다.

문서 묶음의 페이지는 예외다. 제목 아래 lede가 "무엇을 다루는가"에 이미 답하므로, 개요
문단은 "읽으면 알 수 있다"로 쓰지 않고 주제의 정의로 시작한다(`../templates/doc_set.md`
"페이지 골격").

## 4. 제목 (`architecture/heading.mdx`)

문서 제목과 섹션 헤딩에 적용한다.

- **핵심 키워드를 넣는다** — 대상 기능·에러명·결정 사항이 제목만으로 드러나게.
  Don't: "에러를 해결하는 방법은?" / Do: "NOT_FOUND_USER 에러 해결 방법".
- **무엇을 다루는지 모를 제목을 쓰지 않는다** — 대상을 이름으로 부른다.
  Don't: "두 키를 나눈 이유" / Do: "읽기 키와 쓰기 키의 분리 기준".
- **30자 이내, 평서문** — 물음표·느낌표를 쓰지 않는다.
- **같은 레벨 헤딩은 문형을 통일한다** — 기본은 명사형("재시도 정책", "오류 응답")이다.
  "~이란", "~하기", "~할 때"를 같은 레벨에 섞지 않는다. 절차의 단계 제목에는 번호를
  붙인다.
- **헤딩은 H3까지** — H4가 필요하면 분할 신호다(§11).

## 5. 용어 (`sentence/consistency.mdx`, `architecture/predictability.mdx`, `architecture/background.mdx`)

- 쉬운 말이 있으면 쉬운 말을 쓴다. 코드 식별자·도메인 용어·기술 용어는 영어 원어 그대로
  써도 된다. 독자가 모를 수 있는 개념은 **첫 등장 위치에서** 한두 문장으로 정의한다.
  "직교성", "멱등성" 같은 말을 설명 없이 던지지 않는다.
- **한 개념은 한 이름으로** — 한 문서 안에서 "업로드/첨부/넣기", "저장소/DB"처럼 동의어를
  섞지 않는다. 첫 등장 때 고른 용어를 끝까지 쓴다.
- **한 낱말은 한 개념에만** — 같은 낱말이 두 대상을 가리키지 않게 한다.
  Don't: "키"가 API 키, 캐시 키, 정렬 키를 모두 가리킨다. / Do: 각각 "API 키",
  "캐시 키", "정렬 기준"으로 부른다.
- **이름이 문서의 다른 개념과 부딪히는 필드에는 주석을 단다** — 바꿀 수 없는 필드
  이름이면 첫 등장에 "이름과 달리 X와 무관하다"를 적는다.
- **영문 약어는 첫 등장 시 풀어 쓴다** — `SSR(Server-Side Rendering)` 식으로, 약어와
  괄호는 붙여 쓴다. 이후에는 약어만 쓴다. 용어가 많은 문서는 용어 표(§14)를 둔다.
- **공식 표기를 따른다** — "K8" 같은 구어체 대신 "쿠버네티스(Kubernetes)". 대소문자는
  공식 문서 기준.

## 6. 문장 (`sentence/subject.mdx`, `sentence/concreteness.mdx`, `sentence/compactness.mdx`, `sentence/natural-kor-expression.mdx`)

- **능동형, 행위자를 밝힌다** — 수동형("설정이 완료되어야 합니다")보다 능동형("설정을
  완료하세요")으로 쓴다. 독자가 할 일은 독자가 주체다. 시스템의 동작을 설명할 때는
  누가 무엇을 어디에 하는지 밝힌다.
  Don't: "파일을 업로드하면 자동으로 저장됩니다." / Do: "사용자가 파일을 업로드하면
  서버가 스토리지에 저장합니다."
- **군더더기 한자어·명사화 제거** — "수행하다/진행하다/실시하다"는 대부분 빼도 뜻이
  통한다. 명사 나열 대신 동사로 쓴다.
  Don't: "설정 변경을 수행한 후 적용을 진행합니다." / Do: "설정을 바꾼 뒤 적용합니다."
- **메타 담화 금지** — "앞서 설명했듯이", "위 표처럼", "사실은", "아시겠지만" 같은
  말에-대한-말은 핵심 전달을 방해할 뿐이다. 지운다.
- **한 문장 한 생각** — 두 아이디어가 접속어미로 이어져 길어지면 문장을 나눈다.
- **모호한 양 대신 수치** — "여러 번", "현재 규모", "많을 때" 대신 "최대 3번",
  "하루 2만 건", "10,000건을 넘으면"으로 쓴다.
- **확인된 사실은 확정적으로** — 근거가 있으면 "~할 수도 있습니다" 같은 헤지 대신
  조건과 수치로 단정한다("10,000건을 넘으면 응답이 1초 이상 걸린다"). 확인되지 않은
  것은 얼버무리는 대신 미확인임을 명시하거나 공란으로 남긴다 — 없는 사실을 단정하라는
  뜻이 아니다(각 스킬의 "자명한 사실만" 규율이 우선).

## 7. 목록형 서술

본문은 줄글보다 목록으로 쓴다. 문단 산문은 개요·lede처럼 짧은 도입에 쓴다.

- **굵은 리드는 한 문장으로 끝낸다** — 주장 하나를 굵게 쓰고, 이유·조건·예외는 하위
  글머리로 내린다. 같은 줄에 설명을 이어 쓰지 않는다.
  Don't: `- **재시도는 3번까지입니다.** 그 뒤에는 실패로 기록하고 알람을 보냅니다.`
  Do: `- **재시도는 3번까지입니다.**` 아래에 `  - 그 뒤에는 실패로 기록합니다.`
- **정의 목록은 `**용어**: 정의`** 형식으로 쓴다.
- **`**라벨.**` 형식은 번호 단계에만** 쓴다(`1. **준비.** …`).
- **굵은 리드는 하위 글머리를 거느린 주장에만** 쓴다. 하위 설명이 없는 짧은 사실만 모인
  목록은 굵게 쓰지 않는다.
- **한 목록 안에서 굵은 항목과 굵지 않은 항목을 섞지 않는다.** 굵은 리드에 붙는 상호
  참조(§14)는 하위 글머리 끝에 둔다.
- 각 항목은 명사구 조각이 아니라 완결된 문장으로 쓴다.

## 8. 금지 패턴

AI 티가 나는 대표 패턴들. 발견 즉시 고친다.

- 상투적 연결어: "~를 통해", "~를 활용하여", "~함으로써"의 남용.
- 과장 수식어: "강력한", "핵심적인", "혁신적인" 등 정보 없는 형용사.
- 화살표 체인: `A → B → 실패` 식 압축 표기를 문장 대신 쓰는 것. (상호 참조 `→ [링크]`는
  §14 형식이라 해당하지 않는다.)
- 3항목 강박: 모든 나열을 기계적으로 3개씩 맞추는 것.
- bold 남발(§7의 굵은 리드 외의 bold), 문서 길이에 비해 과도한 헤더 쪼개기, 장식용 이모지.

## 9. 시각 밀도

문단은 2~4문장. 표는 짧은 사실 나열에만 쓰고, 설명·해석은 표 밖에 둔다.
callout(강조 박스)은 문서당 소수만 — 전부 강조하면 아무것도 강조되지 않는다.

## 10. 간결 ≠ 압축

짧게 쓰되 조각내지 않는다. 분량을 줄일 때 빼는 것은 문장 성분이 아니라 내용이다 —
독자의 이해나 다음 행동에 영향 없는 디테일을 통째로 덜어내고, 남긴 내용은 완결된
문장으로 쓴다.

## 11. 분할 신호 (`architecture/one-thing-per-one-page.mdx`)

다음 중 하나라도 해당하면 이 산출물은 한 그릇에 담을 내용이 아니라는 신호다.

1. 헤딩이 H4(`####`) 이상으로 파여야 내용이 정리된다.
2. 서로 독립적인 핵심 주제가 2개 이상이다 — 한 주제를 통째로 들어내도 나머지가
   완결되면 독립이다.
3. 유형별 분량 규격을 초과한다(예: proposal_chat 15줄).

신호가 뜨면 **억지로 한 산출물에 욱여넣지 말고 멈춰서 사용자에게 대응을 제안한다.**
자동으로 분할하지 않으며, 사용자가 이미 단일 산출물을 명시했으면 다시 묻지 않는다.
대응은 유형에 따라 다르다:

| 산출물 유형 | 신호가 드러내는 것 | 제안할 대응 |
|---|---|---|
| 일반 문서 (refactor 산출물, general) | 한 문서에 담을 양이 아님 | 허브 + 유형별 페이지의 문서 묶음(`../templates/doc_set.md`) |
| 문서 묶음의 한 페이지 | 페이지가 두 주제를 다룸 | 페이지를 둘로 나누고 문서 지도에 추가 |
| issue/bug 티켓 | 티켓 스코프가 큼 | 티켓을 2개 이상으로 분리 |
| PR 본문 | 문서가 아니라 PR 자체가 큼 | PR 분할(커밋 재구성) 신호를 보고 |
| proposal_chat | 채팅 규격에 담을 내용이 아님 | 정식 문서 유형으로 승격 |
| diff_explanation | diff가 여러 관심사를 섞음 | 해설을 챕터로 분리, 심하면 PR 분할 신호 보고 |
| wiki REPORT | 결정 도메인 혼입 | REPORT 분할(write-wiki 스킬 규칙 참조) |

## 12. 표기

한국어 본문에 한자(漢字)·중국어 문자를 노출하지 않는다. 한자어를 쓰는 것과는 다른 문제로,
여기서 막는 것은 글자 자체가 본문에 찍혀 나오는 것이다. 원어 병기가 꼭 필요한 고유명사나
인용은 괄호 안에 한 번만 허용한다.

- 나쁨: 이 값은 캐시에 저장(貯藏)되며 다음 요청時 재사용된다.
- 좋음: 이 값은 캐시에 저장되며 다음 요청 때 재사용된다.

오탈자와 띄어쓰기 오류를 남기지 않는다. 특히 조사·어미가 붙은 채 잘린 문장, 붙여 써야 할
합성어를 띄어 쓴 것을 확인한다. 영문·숫자·코드 식별자 뒤에 오는 조사는 띄어 쓴다
(`API 를`, `job 이`, `` `201` 을 ``) — 팀 규약이다.

같은 대상을 한글과 영문으로 번갈아 쓰지 않고 문서 안에서 한 표기로 고정한다. 코드 식별자와
도메인 용어는 원어를 유지하되, 한 번 정한 표기를 끝까지 쓴다.

- 나쁨: 임베딩 벡터를 캐시에 넣는다. 이후 embedding은 캐시에서 읽는다.
- 좋음: 임베딩을 캐시에 넣는다. 이후 임베딩은 캐시에서 읽는다.

산출 문서에 작성에 쓴 개인 도구·스킬·플러그인 이름을 노출하지 않는다.

## 13. 어미 (`overview.md` 참고사항)

기본은 합니다체("~합니다", "~하세요")다. 요청자가 해요체 등 다른 어미를 지정하면 따른다.
토스 가이드는 어미를 문서 분위기에 맞춰 자유롭게 고르게 둔다. 어느 쪽이든 한 문서(묶음) 안에서는
하나로 통일한다.

## 14. 형식 통일 (`architecture/predictability.mdx`)

같은 종류의 정보는 문서(묶음) 전체에서 같은 형식으로 쓴다. 독자가 한 번 익힌 형식을
다른 곳에서도 그대로 읽게 하기 위해서다.

- **표 헤더 어휘를 고정한다.**
  - 열거값 표: `값 | 뜻`
  - 필드 표: `필드 | 필수 | 설명`
  - API 목록: `API | 하는 일 | 응답`
  - 응답 필드 표: `필드 | 설명`
  - 오류 표: `상태 | 원인 | 할 일` ("할 일"은 독자가 할 행동으로 쓴다)
  - 용어 표: `용어 | 뜻 | 자세히`, 약어 표: `약어 | 풀이`
- **상호 참조는 항목 끝에 `→ [페이지 제목](링크)`** 로 단다. 링크 이름은 대상 페이지의
  H1과 같게 쓴다. 다른 문서를 이름으로 언급하면 반드시 링크를 단다
  (`sentence/concreteness.mdx` "참조되는 내용의 맥락을 설명하세요").
- **출처는 `기관/저자, 제목, §절. [도메인](URL)`** 로 쓴다.
  - 본문에서 인용하지 않는 출처는 넣지 않는다.
  - 출처 하나에 번호 하나를 쓰고, 본문에서는 "(출처 1)"로 가리킨다.
- **코드·값 표기**
  - 필드 값은 JSON 그대로 쓴다(`"status": "failed"`).
  - 요청 예제는 `http` 코드 블록으로, 그대로 보낼 수 있게 인증 헤더까지 쓴다. 비밀값·환경별
    값은 `<Admin 토큰>`, `<호스트>` 같은 자리표시자로 두되, 근거에 없는 필드 이름·값은
    지어내지 않는다 — 예제를 쓸 근거가 없으면 공란 규칙을 따른다.
  - JSON 블록 안에 주석을 넣지 않는다. 설명은 블록 밖에 둔다.
  - 설계 문서는 의사코드까지만 내려간다. 의사코드 블록은 첫 줄을 `# 의사코드`로 연다.
  - 실제 데이터가 아닌 예시에는 "설명용 예시" 라벨을 붙인다.

## 템플릿과의 관계

유형별 형식 제약(예: proposal_chat의 헤딩 없는 15줄 이내 단문, diff_explanation의 산문
Background·Intuition, pull_request의 한 문단 한 줄, experiment_report의 과정 기록 섹션)은 해당 템플릿의 명시가 이 가이드보다 우선한다. 명시가 없는 부분은 이 가이드를
따른다.
