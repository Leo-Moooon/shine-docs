# 문체 스타일 가이드 (writing-style)

모든 산출물에 적용하는 표현 층위 규칙. 템플릿이 "어떤 섹션을 어떤 순서로"를 정한다면,
이 가이드는 "문장을 어떻게 쓰나"를 정한다. **작성자는 초안 전에 정독하고, 가독성 리뷰어는
아래 규칙 위반을 반려 사유로 삼는다** (리뷰어용 판정 목록은 `review-checklist.md` 참조).
목표 문체: 간결한 실무체 — 동료에게 공유하기 위한 문서라는 전제를 항상 깔고 쓴다.

## 1. 최종 상태만, flat하게 (최우선 규칙)

문서는 작업의 연대기가 아니라 결론의 전달이다. "처음엔 A로 했다가 → 문제를 발견해서 →
B로 바꿨고 → 최종적으로는" 같은 과정 서술을 본문 논리 구조로 쓰지 않는다. 서술 순서는
시간순이 아니라 최종 내용 기준으로 짠다: **지금 무엇인가 → 왜 그런가.**

과정·시행착오 trace가 독자에게 실제로 중요한 경우(실험 리포트의 실패 기록, 검토했으나
기각한 대안 등)에만 별도 섹션("검토한 대안", "시행착오" 등)으로 격리해서 담고, 본문
서술에 섞지 않는다.

## 2. 독자 상정

독자는 동료다 — 팀·레포의 일반 맥락은 알지만, 이 문서가 다루는 변경·논의·실험은 모른다.
모든 용어 선택과 배경 설명의 깊이는 이 독자를 기준으로 정한다.

## 3. 개요는 가치를 먼저

요약/개요 섹션은 "이 문서를 읽으면 무엇을 알게 되거나 할 수 있게 되는가"에 먼저 답한다.
배경 지식, 도입 경위, 일반론은 그다음이다. 독자는 개요만 읽고 이 문서가 자기 문제와
관련 있는지 판단한다.

- Don't: "이 문서는 재시도 로직의 도입 배경과 구현을 소개합니다. 재시도란…"
- Do: "이 문서를 읽으면 API 요청 실패 시 자동 재시도를 어떻게 붙이는지 알 수 있다."

## 4. 제목

문서 제목과 섹션 헤딩에 적용한다.

- **핵심 키워드를 넣는다** — 대상 기능·에러명·결정 사항이 제목만으로 드러나게.
  Don't: "에러를 해결하는 방법은?" / Do: "NOT_FOUND_USER 에러 해결 방법".
- **30자 내외, 평서문** — 물음표·느낌표를 쓰지 않는다.
- **같은 레벨 헤딩은 문형을 통일한다** — 동사형("~하기")이면 전부 동사형, 명사형이면
  전부 명사형.

## 5. 용어

- 쉬운 말이 있으면 쉬운 말을 쓴다. 코드 식별자·도메인 용어는 원어를 유지하되, 독자가
  모를 수 있는 개념이 처음 등장하면 한 문장으로 풀어 준다. "직교성", "멱등성" 같은 말을
  설명 없이 던지지 않는다.
- **같은 개념에는 같은 용어** — 한 문서 안에서 "업로드/첨부/넣기"처럼 동의어를 섞지
  않는다. 첫 등장 때 고른 용어를 끝까지 쓴다.
- **영문 약어는 첫 등장 시 풀어 쓴다** — `SSR(Server-Side Rendering)` 식으로, 약어와
  괄호는 붙여 쓴다. 이후에는 약어만 쓴다.
- **공식 표기를 따른다** — "K8" 같은 구어체 대신 "쿠버네티스(Kubernetes)". 대소문자는
  공식 문서 기준.

## 6. 문장

- **능동형, 독자 주체** — 수동형("설정이 완료되어야 합니다")보다 능동형("설정을
  완료하세요")으로 쓴다. 문서의 행동 주체는 독자다. 단 도구·시스템의 동작 방식 자체를
  설명할 때는 도구를 주어로 써도 된다.
- **군더더기 한자어·명사화 제거** — "수행하다/진행하다/실시하다"는 대부분 빼도 뜻이
  통한다. 명사 나열 대신 동사로 쓴다.
  Don't: "설정 변경을 수행한 후 적용을 진행합니다." / Do: "설정을 바꾼 뒤 적용합니다."
- **메타 담화 금지** — "앞서 설명했듯이", "사실은", "아시겠지만" 같은 말에-대한-말은
  핵심 전달을 방해할 뿐이다. 지운다.
- **한 문장 한 생각** — 두 아이디어가 접속어미로 이어져 길어지면 문장을 나눈다.
- **확인된 사실은 확정적으로** — 근거가 있으면 "~할 수도 있습니다" 같은 헤지 대신
  조건과 수치로 단정한다("10,000건을 넘으면 응답이 1초 이상 걸린다"). 확인되지 않은
  것은 얼버무리는 대신 미확인임을 명시하거나 공란으로 남긴다 — 없는 사실을 단정하라는
  뜻이 아니다(각 스킬의 "자명한 사실만" 규율이 우선).

## 7. bullet 사용 기준

bullet은 진짜 병렬 나열(항목 목록, 체크리스트, 옵션 비교)일 때만 쓴다. 논리 전개
(왜 → 그래서 → 결과)는 문단 산문으로 쓴다. bullet을 쓸 때도 각 항목은 명사구 조각이
아니라 완결된 문장으로 쓴다.

## 8. 금지 패턴

AI 티가 나는 대표 패턴들. 발견 즉시 고친다.

- 상투적 연결어: "~를 통해", "~를 활용하여", "~함으로써"의 남용.
- 과장 수식어: "강력한", "핵심적인", "혁신적인" 등 정보 없는 형용사.
- 화살표 체인: `A → B → 실패` 식 압축 표기를 산문 대신 쓰는 것.
- 3항목 강박: 모든 나열을 기계적으로 3개씩 맞추는 것.
- bold 남발, 문서 길이에 비해 과도한 헤더 쪼개기, 장식용 이모지.

## 9. 시각 밀도

문단은 2~4문장. 표는 짧은 사실 나열에만 쓰고, 설명·해석은 표 밖 산문에 둔다.
callout(강조 박스)은 문서당 소수만 — 전부 강조하면 아무것도 강조되지 않는다.

## 10. 간결 ≠ 압축

짧게 쓰되 조각내지 않는다. 분량을 줄일 때 빼는 것은 문장 성분이 아니라 내용이다 —
독자의 이해나 다음 행동에 영향 없는 디테일을 통째로 덜어내고, 남긴 내용은 완결된
문장으로 쓴다.

## 11. 분할 신호

다음 중 하나라도 해당하면 이 산출물은 한 그릇에 담을 내용이 아니라는 신호다.

1. 헤딩이 H4(`####`) 이상으로 파여야 내용이 정리된다.
2. 서로 독립적인 핵심 주제가 2개 이상이다 — 한 주제를 통째로 들어내도 나머지가
   완결되면 독립이다.
3. 유형별 분량 규격을 초과한다(예: proposal_chat 15줄).

신호가 뜨면 **억지로 한 산출물에 욱여넣지 말고 멈춰서 사용자에게 대응을 제안한다.**
자동으로 분할하지 않으며, 사용자가 이미 단일 산출물을 명시했으면 다시 묻지 않는다.
대응은 유형에 따라 다르다:

| 산출물 유형 | 신호가 드러내는 것 | 제안할 대응 |
|---|---|---|
| 일반 문서 (refactor 산출물, general) | 한 문서에 담을 양이 아님 | 개요(허브) 문서 + 하위 문서로 분할 |
| issue/bug 티켓 | 티켓 스코프가 큼 | 티켓을 2개 이상으로 분리 |
| PR 본문 | 문서가 아니라 PR 자체가 큼 | PR 분할(커밋 재구성) 신호를 보고 |
| proposal_chat | 채팅 규격에 담을 내용이 아님 | 정식 문서 유형으로 승격 |
| diff_explanation | diff가 여러 관심사를 섞음 | 해설을 챕터로 분리, 심하면 PR 분할 신호 보고 |
| wiki REPORT | 결정 도메인 혼입 | REPORT 분할(write-wiki 스킬 규칙 참조) |

## 템플릿과의 관계

유형별 형식 제약(예: proposal_chat의 bullet 중심 단문, experiment_report의 과정 기록
섹션)은 해당 템플릿의 명시가 이 가이드보다 우선한다. 명시가 없는 부분은 이 가이드를
따른다.
