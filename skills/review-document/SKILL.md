# Review Document

문서 품질 판정의 단일 원본. 검사 축의 정의, 리뷰어 배분, 판정 등급, 리포트 형식을 여기서
정한다.

## 호출 방식 두 가지

**공용 엔진** — `write-document` §4, `document-refactor` §4가 호출한다. 초안·근거·템플릿이
호출부에서 넘어오므로 Intake를 건너뛴다. **지적과 수정 제안까지만 내고 멈춘다** — 반영은
호출부의 작성자 컨텍스트가 한다. 리뷰어가 남의 초안을 직접 고치면 작성자와 리뷰어의 경계가
무너진다. 라운드 루프도 호출부가 관리하며, 이 스킬에게는 1회 호출이 1라운드다.

**단독 진입점** — 이미 있는 문서를 리뷰한다. 근거와 수정 권한을 Intake에서 묻고, 승인된
권한 범위 안에서 반영까지 한다.

범위 밖: 문서를 새로 쓰거나(→ `write-document`) 재구조화하지 않고(→ `document-refactor`),
티켓·PR 시스템에 반영하지 않는다.

## 1. Intake (단독 호출 전용)

클릭형 선택지 도구(harness의 AskUserQuestion 등)로 묻고, 없는 환경이면 텍스트로 폴백한다.
사용자가 처음부터 값을 명시한 항목은 다시 묻지 않는다.

- **대조 근거**: 「원문 파일·URL 지정」 / 「코드베이스」 / 「없음(문서만)」. 사실성 게이트의
  기준선을 정한다.
- **수정 권한**: 「지적만 하고 멈춤」 / 「항목별로 승인받고 수정」 / 「알아서 수정하고 보고」.
- **문서 유형**: 공용 템플릿 풀 `../templates/`에서 추정해 확인받는다. 실행가능성 축을
  적용할지와 공란 규율을 판정할 템플릿이 여기서 정해진다.

## 2. 두 리뷰어 실행

축은 여덟 개이고, **무엇을 손에 들고 있어야 판정되는가**로 배분한다. 두 리뷰어는 서로
분리된 컨텍스트여야 하며, 초안을 쓴 작성자와도 분리되어야 한다(자기검토 금지).

### 검증 리뷰어 — `../style/verification-checklist.md` 순회

문서 밖 자료를 들고 대조한다. **외부 조회 권한(코드베이스 탐색, 웹검색, URL fetch)은 이
리뷰어에게만 있다.** 담당 축은 사실성(하드 게이트), 참조 유효성, 공란 규율.

근거가 "없음"이면 사실성 게이트는 비활성이다. 코드베이스가 있으면 참조 유효성만 보고,
문서가 스스로 검증 가능한 주장을 했을 때만 확인해 질문으로 올린다.

### 가독성 리뷰어 — `../style/review-checklist.md` 순회

**문서 텍스트만 받는다. 근거 원문을 주지 않는 것이 설계 의도다** — 문서가 스스로 성립하는지
보는 역할인데 배경 지식을 쥐여주면 독자 적합성 축이 무력화된다. 담당 축은 가독성·구조,
내부 일관성, 독자 적합성, 표기, 실행가능성.

문체·표기 축의 규칙 원문은 `../style/writing-style.md`다. 아래 두 축의 규칙 원문은 이
문서가 갖는다.

**내부 일관성.** 문서 자기 자신과의 대조다. 앞뒤 주장의 모순, 요약과 본문 표의 수치 불일치,
같은 대상을 두 이름으로 부르는 것, 목차와 실제 섹션 구성의 불일치. 외부 근거 없이 판정되고
오탐이 거의 없어, 근거를 못 받은 리뷰에서도 그대로 작동한다.

**실행가능성.** `issue_ticket`, `bug_ticket`, `pull_request`에만 적용한다. 읽고 나서 무엇을
해야 하는지가 나오는가 — 재현 절차, 수용 기준, 검증 방법. `general`과 `diff_explanation`은
독자를 이해시키는 것이 목적이므로 적용하지 않는다.

## 3. 판정

세 등급으로 통합한다.

| 등급 | 대상 | 결과 |
|---|---|---|
| 하드 게이트 반려 | 사실성 위반 | 하나라도 있으면 통과 불가 |
| 수정 요구 | 나머지 일곱 축의 명확한 위반 | 반영 후 재판정 |
| 질문 | 근거 부족으로 판정이 갈리는 것, 웹검색으로 찾은 원문 자체의 오류 | 반려 아님 |

웹검색 결과를 반려 근거로 쓰지 않는다. `document-refactor`의 판정 기준은 "원문 대비
충실도"이지 세상의 진실이 아니다. 검색으로 잡은 오류가 원문에서 온 것이라면 산출물의 결함이
아니므로 "원문의 결함"으로 따로 표시한다.

오탐 억제 규율을 지킨다. 문서를 더 풍부하게 만들라고 요구하지 않고, 근거가 없어 공란인
섹션은 정상 동작이므로 감점하지 않는다.

## 4. 리포트

판정 한 줄로 시작한다(통과 / 수정 요구 / 하드 게이트 반려). 지적은 축별로 묶고, 항목마다
문제가 있는 위치를 인용하고, 위반한 축과 근거가 되는 절을 밝히고, 수정 제안을 단다. 질문은
지적과 섞지 않고 따로 모은다.

```
판정: 수정 요구 (하드 게이트 통과)

## 독자 적합성
- "ML-1086 반영 후 재배포" — 티켓이 무엇을 다루는지 밝히지 않았다.
  제안: "설정 API를 추가한 ML-1086 반영 후 재배포"

## 표기
- "다음 요청時" — 한자 노출 (writing-style §12).
  제안: "다음 요청 때"

## 질문
- "p95 240ms" 수치의 출처를 근거에서 찾지 못했다. 어디서 온 값인가?
```

## 5. 반영 (단독 호출 전용)

Intake에서 승인된 수정 권한을 따른다. 「지적만」이면 리포트에서 멈추고, 「승인받고 수정」이면
항목별로 확인한 뒤 반영하고, 「알아서 수정」이면 반영한 다음 무엇을 왜 고쳤는지 보고한다.

사실성 지적은 어느 권한에서든 자동으로 고치지 않는다. 원래 작성자만 아는 정보가 필요한
경우가 대부분이라 억측이 섞인다 — 해당 항목은 항상 지적으로 남긴다.
