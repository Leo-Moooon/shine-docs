# PR 본문 (pull_request)

지금 열 Pull Request의 설명 본문. (작성용 — write-document. 이미 머지된 변경의 사후 설명은 `pr_retrospective` 참조.)

## 섹션
- **요약** [필수] — 이 PR이 무엇을 하는가. **효과를 수치로 먼저** 쓰고, 리뷰어가 첫 줄에서 오해할 만한 것을 여기서 부정한다("파라미터는 바꾸지 않습니다").
- **배경/동기** [필수] — 왜 필요한가. 기존 상태가 왜 문제였는지를 관측된 사실로 적는다.
- **변경 내용** [필수] — 무엇이 어떻게 바뀌었나. 파일·대상이 여럿이면 표로.
- **검증** [필수] — 실행한 명령·테스트와 **그 결과**. 실행하지 않았으면 그렇게 적는다.
- **범위 제외/후속** [필수] — 이번 PR에서 뺀 것과 이유. **뺀 대상마다 근거를 붙인다** — 목록만 있으면 리뷰어가 누락인지 판단인지 못 가른다.
- **영향 범위/호환성** [선택] — breaking change·마이그레이션 필요 여부.
- **리뷰 포인트** [선택] — 어디를 집중해서 봐 달라. **판단이 필요한 지점을 지목**한다("이 diff가 최소 삽입인지"). "꼼꼼히 봐 달라"는 정보가 없다.
- **알려진 한계** [선택] — 구조적으로 남는 제약. 미검증 리스크가 있으면 **무엇이·언제·누가 그것을 닫는지**까지 적는다.

## 작성 규율

**형용사 대신 수치.** "크게 개선했습니다"가 아니라 "29/30 → 0/30". 개선폭을 못 재는 항목은 못 잰다고 적는다.

**기각한 대안을 남긴다.** 채택하지 않은 선택지와 그 이유가 없으면, 리뷰어는 검토했는지 몰랐는지 구분할 수 없다. 대안 비교가 결정의 근거라면 검증 절에 나란히 놓는다.

**측정값에는 비교 기준을 함께 준다.** "변경률 3.3%"만으로는 판단이 안 된다. 무엇과 견준 값인지(기준선·자기변동·임계) 같은 표에 둔다.

**추론과 측정을 섞지 않는다.** 재보지 않고 다른 사례를 준용했다면 그렇게 밝힌다.

## 형식

**문단을 하드 랩하지 않는다.** GitHub은 PR·이슈 본문에서 단일 개행도 줄바꿈으로 렌더링한다. 편집기 관례대로 80~100자에서 끊으면 문장이 중간에서 잘려 보인다. 한 문단 = 한 줄로 쓰고, 문단 사이만 빈 줄로 나눈다. 표·목록·코드블록은 자체 줄을 유지한다.

**나열은 표로.** 파일별 변경, 대상별 판정, 구성별 측정처럼 열이 같은 항목은 산문보다 표가 읽힌다.

**스택 PR이면 관계를 밝힌다.** base가 다른 PR이면 근거 문서가 어느 PR에 있는지 본문에서 가리킨다.

## 문체

**존댓말(합니다체).** 팀이 읽는 글이고 리뷰 요청이 섞이므로 평서체(`~한다`)보다 맞는다. 같은 티켓의 실험 리포트·설계 문서가 평서체여도 PR 본문은 존댓말로 쓴다.
