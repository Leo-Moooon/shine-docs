# 문서 묶음 (doc_set)

한 주제를 허브 페이지 + 유형별 페이지 여러 장으로 쓰는 문서(설계서 묶음, 서비스 문서 등). (작성용 — write-document. 단일 문서가 분할 신호에 걸렸을 때의 허브 분할에도 이 골격을 쓴다.)

괄호 안 경로는 근거가 된 토스 테크니컬 라이팅 가이드 원문 파일이다(`docs/` 기준, 출처는 `../style/writing-style.md` 끝).

## 묶음 규칙
- **페이지 목록이 원본이다** — 파일·제목·유형·lede·주 독자를 한 목록에 두고, H1·lede·사이드바·문서 지도·이전/다음을 모두 여기서 만든다. 문서 지도의 "다루는 것"과 각 페이지 lede가 어긋나지 않게 하는 장치다.
- **한 페이지 한 주제** — 페이지가 독립 주제를 둘 이상 다루면 나눈다. 묶음 설계는 사이드바 메뉴를 짜는 것부터 시작한다 (`architecture/one-thing-per-one-page.mdx`, `tutorial/structure.mdx`).
- **원본은 한 페이지에만** — 같은 내용을 여러 페이지에 쓰지 않는다. 원본 페이지 밖에서는 결론 한 줄과 `→ [페이지 제목](링크)`만 남긴다. 중복은 고칠 때 한쪽만 바뀌어 어긋난다 (`architecture/one-thing-per-one-page.mdx` "문서 유지보수가 쉬워요").
- **이름 하나** — 용어 페이지에 정한 이름을 모든 페이지에서 쓴다 (`architecture/predictability.mdx`).
- **첫 등장 정의는 페이지 기준** — 페이지마다 처음 나오는 용어에 한 줄 뜻과 `→ [용어](glossary 링크)`를 단다. 긴 정의는 원본 페이지 한 곳에만 둔다.
- **크로스링크** — 허브는 모든 페이지를 링크한다. 상호 참조 형식은 `../style/writing-style.md` §14 (`tutorial/structure.mdx` §3).
- **어미·형식은 묶음 전체에서 하나** — `../style/writing-style.md` §13·§14.

## 페이지 유형
페이지마다 학습·문제 해결·참조·설명 중 유형을 하나 정하고 그 요건(`../style/doc-types.md`)을 지킨다. 부록(설계 결정·용어)은 아래 "부록 페이지"를 따른다.

## 허브 페이지
허브도 아래 "페이지 골격"을 따른다. 개요 문단 뒤 H2는 아래 넷만 이 순서로 둔다.

- **서비스가 하는 일** [필수] — 이 주제(서비스)가 하는 일. 굵은 리드 + 하위 글머리, 원리는 한 줄과 `→ [페이지 제목](링크)`만.
- **흐름** [선택] — 다이어그램 + 번호 단계. 단계마다 한 줄로 쓰고 끝에 `→ [페이지 제목](링크)`. 단계의 원리는 해당 페이지가 원본이다.
- **문서 지도** [필수] — 표 `유형 | 문서 | 다루는 것 | 주 독자`. 허브 자신은 넣지 않는다. "다루는 것" 칸은 페이지 목록의 lede다. 근거가 없는 칸은 `—`로 두고 사유를 표 아래 한 줄로 적는다.
- **원칙** [선택] — 묶음 전체에 걸친 원칙. 번호(R1, R2…)를 붙여 다른 페이지가 인용하게 한다.

이 밖의 내용은 허브에 H2로 두지 않는다. 목표·마일스톤·작업 범위·알려진 위험·도메인 모델·조사 방법·출처 목록처럼 허브에 쌓이기 쉬운 것은 각자 원본 페이지(대개 부록)로 옮기고, 허브에는 필요하면 "서비스가 하는 일"이나 문서 지도 아래 한 줄과 링크만 남긴다. 허브가 길어지면 독자가 문서 지도에 닿기 전에 지친다.

## 페이지 골격 (모든 페이지 공통)
- **H1** [필수] — 페이지 제목. 사이드바·문서 지도·상호 참조 링크 이름과 같다. 페이지 전체가 미확정이면 상태 칩을 단다(아래 "상태 표시").
- **lede** [필수] — 한 줄 요약. 묶음 전체에서 한 형식으로 쓴다(예: "~를 다룹니다.").
- **개요 문단** [필수] — 개요 문단은 주제의 정의로 시작한다. 첫 문장은 "content-labeler 는 …하는 서비스입니다", "job 은 …입니다"처럼 페이지 주제가 무엇인지 말하고, 다음 문장들이 그 주제의 핵심 동작이나 경계를 잇는다. 2~4문장.
  - "이 페이지는 …", "이 페이지를 읽으면 … 알 수 있습니다", "이 묶음을 읽으면 …"으로 쓰지 않는다. 문서 자신을 가리키는 메타 담화이고, 페이지가 무엇을 다루는지는 바로 위 lede가 이미 말했다(lede 반복). `../style/writing-style.md` §3의 "읽으면 알 수 있다" 문형은 lede가 없는 단일 문서용이다.
  - Don't: "이 페이지를 읽으면 job 이 언제 처리되는지 알 수 있습니다."
  - Do: "job 은 문항 하나를 라벨링하는 작업 단위입니다. API 가 문항을 받으면 job 을 큐에 넣고, worker loop 가 하나씩 꺼내 처리합니다."
- **상태 콜아웃** [선택] — 페이지 전체가 미확정일 때 무엇이 왜 미확정인지. 개요 문단 바로 아래에 하나만 둔다. 콜아웃은 이 한 종류뿐이다 — 강조·팁·주의용 콜아웃을 따로 만들지 않는다.
- **본문** [필수] — H2 절. 헤딩 깊이는 writing-style §4.
- **출처** [선택] — 본문에서 인용한 것만. 형식은 `../style/writing-style.md` §14.

## 부록 페이지
- **설계 결정** [선택] — 택한 결정과 근거 / 검토한 대안 표(writing-style §1) / 다루지 않는 것(Out-of-Scope, 항목마다 `후속` 또는 `범위 밖` 칩).
- **용어** [선택] — 용어 표와 약어 표(헤더는 writing-style §14). "자세히"는 정의가 있는 페이지로의 링크이고, 원본 페이지가 없는 용어는 `—`로 둔다.
- **그 밖의 부록** [선택] — 목표·마일스톤·작업 범위·알려진 위험·조사 방법처럼 허브에 두지 않는 것. 한 페이지 한 주제를 지켜 필요한 만큼 나눈다.

## 상태 표시
미확정·후속·범위 밖은 상태 칩 세 가지로만 표시한다. 본문에 "(제안)", "(미정)", "(TBD)" 같은 괄호 텍스트를 달지 않는다 — 문장마다 붙기 시작하면 무엇이 확정인지 오히려 안 보인다.

| 칩 | 뜻 |
|---|---|
| `TBD` | 정해지는 중이다. 확정되면 칩을 뗀다 |
| `후속` | 지금은 하지 않지만 조건이 생기면 다시 본다 |
| `범위 밖` | 이 설계가 다루지 않는다 |

- **페이지 전체**가 미확정이면 페이지 목록에 상태를 적는다 — 페이지 제목·사이드바·문서 지도에 칩이 붙는다. 무엇이 미확정인지는 상태 콜아웃에 쓴다.
- **항목 하나**가 미확정이면 그 목록 항목 맨 앞에 칩을 단다. 리드 문장은 확정된 문장처럼 쓴다(예: `TBD` **최소 문항 수는 0단계 측정 뒤 정합니다.**).
- **다루지 않는 것** 목록은 항목마다 `후속` 또는 `범위 밖` 칩을 단다.

## 산출
- **HTML** — `../style/html-layout.md` "문서 묶음" 절. 셸(`doc_set_shell.css`·`doc_set_shell.html`)을 그대로 쓰고 `scripts/build_doc_set.py`로 빌드한다. 원고 문법(고정 앵커, 상태 칩, 콜아웃, 문서 지도 자리)도 그 절에 있다.
- **Markdown** — 페이지마다 `.md` 한 파일, 허브는 `index.md`, 페이지끼리 상대 링크. 생성 단계가 없으므로 페이지 목록을 확정한 뒤 lede와 문서 지도 행을 그 목록에서 글자 그대로 옮기고, 바꿀 때는 목록부터 고친다. 다이어그램은 mermaid로 그린다(ASCII 금지). 상태 칩은 인라인 코드(`` `TBD` ``)로, 상태 콜아웃은 첫 줄이 `` > `TBD` **제목** ``인 인용 블록으로 쓴다.
