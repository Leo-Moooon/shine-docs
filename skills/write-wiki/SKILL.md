# write-wiki — 티켓 아카이브 작성

티켓 단위 작업이 끝날 때, 개인 옵시디언 vault에 **"어떤 실험·작업을 했고 무엇을 왜
결정했나"**를 남기는 아카이브를 만든다.

**용도는 추후 포트폴리오 정리 시의 원천 데이터**다. 파일 보관이 목적이 아니다 — 그래서
첨부 취사선택보다 **실험 기록과 결정 근거를 문서로 남기는 것**이 언제나 우선이다.
워크트리·브랜치는 사라져도 이 기록은 남는다.

## 절대 규율 (write-document 계승)

- **자명한 사실만**: 대화 맥락·코드베이스·로그에서 확인한 것과 요청자 진술만 쓴다.
  그럴듯한 유추로 빈칸을 채우지 않는다. 근거 없는 필수 항목은 비워 두고
  "무엇이 없어서 비었는지" 한 줄을 남긴다.
- **최종 상태만, flat하게**: 시행착오 연대기가 아니라 결론 중심으로 쓴다.
  과정이 가치 있는 경우(기각한 대안, 실패 run)만 "교훈" 섹션에 격리한다.
  단 **실험은 과정이 아니라 산출물이다** — 이 규칙을 이유로 실험 기록을 압축하지 말 것.
  "무엇을 재서 무엇이 나왔나"는 결론과 같은 위상으로 남긴다.
- 수치를 지어내지 않는다. 실험 수치는 REPORT/결과 파일에서 그대로 가져온다.

## 개인 설정 (전역 설정에서 읽는다)

**vault 루트 경로와 티켓번호 컨벤션은 이 스킬에 하드코딩하지 않는다.** 사용자의 전역
설정(CLAUDE.md 등 하네스 메모리)에서 읽고, 정의되어 있지 않으면 작성 시작 전에
사용자에게 묻는다. 아래 예시의 `ABC-123` 류 티켓번호는 자리표시자다 — 실제로는
사용자의 티켓 컨벤션을 따른다.

## 경로·구조 규칙

```
<vault 루트>/<레포명>/<티켓번호> <간단한 설명>/                  # 최상위 티켓
└── <부모 없으면 여기 파일들>

<vault 루트>/<레포명>/<부모 티켓> <설명>/<자식 티켓> <설명>/     # 파생/하위 티켓은 부모 하위로 중첩
├── <티켓번호> README.md              # 진입점 (필수, 아래 템플릿)
├── <티켓번호> REPORT (<주제>).md     # 실험 1개일 때
├── <티켓번호> REPORT 1 (<주제>).md   # 실험 K개일 때 — 1..K 연번 (아래 규칙)
└── <티켓번호> <증빙>.html|png        # 결과 보고서·스크린샷 등 자기완결 파일
```

- **폴더명 = `<티켓번호> <간단한 설명>`** — 폴더만 보고 그 티켓이 무슨 작업인지 알 수 있게
  짧은 설명을 붙인다(예: `ABC-135 실패모드 카탈로그`). 번호만 있으면 나중에
  포트폴리오 정리 시 폴더 목록이 불투명하다. 설명은 제목의 축약이면 충분.
- **파생/하위 티켓은 부모 티켓 폴더 하위에 중첩** — 링크(`[[부모 README]]`)로도 계보가
  표현되지만, 사람이 트리를 훑을 때 **물리적 중첩이 인지적으로 더 즉각적**이다. 부모가
  분명하면 그 폴더 안에 자식 폴더를 둔다(예: `ABC-132 …/ABC-135 …/`). 링크는 파일명 기반이라
  중첩·이동해도 안 깨진다. 단 **부모가 모호하거나 다중이면 flat 유지 + 링크로만** 표현한다
  (억지 중첩으로 트리를 왜곡하지 말 것). README 본문에도 승계 관계를 한 줄 명시한다.
- **모든 파일명에 티켓번호 접두사** — 폴더에 설명이 붙어도 **파일명은 `<티켓번호>` 접두사만**
  쓴다(폴더 설명을 파일명에 중복하지 않는다). 옵시디언 링크는 파일명 기반이라 `[[README]]`,
  `[[REPORT]]`가 티켓 간 충돌한다. 예외 없음. (폴더명은 링크 키가 아니라 rename해도 링크
  안 깨진다.)
- **README는 목차가 아니다** — 이것만 읽어도 배경·한 일·결정·교훈이 파악되어야 한다.
  REPORT를 분할했어도 README가 얄팍해지지 않는다. 분할로 넘기는 것은 **실험의 방법과
  전체 결과**뿐이고, "무엇을 재서 무엇을 결정했나"는 README의 요약 표에 남는다.
  같은 수치를 양쪽에 쓰지 않는다 — 한쪽만 고쳐지면 어긋난다.
- HTML은 옵시디언에서 렌더링되지 않는다(브라우저 열람 전제) — 서사는 README(md)에
  직접 쓰고 HTML은 증빙 첨부로만 취급한다.

### 실험이 여럿이면 REPORT를 분할한다

한 파일에 몰아넣지 말고 실험 단위로 나눈다. **파일명 규칙은 개수에 따라 갈린다.**

| 실험 수 | 파일명 | 예 |
|---|---|---|
| 1개 | `<티켓번호> REPORT (<주제>).md` — 번호 없음 | `ABC-104 REPORT (sweep 판정).md` |
| K개 | `<티켓번호> REPORT 1..K (<주제>).md` — 1부터 연번 | `ABC-101 REPORT 3 (프록시 수용성).md` |

- 번호는 **읽는 순서**다. 시간순이 아니라 이해 순서로 매긴다(전제 확인 → 값 결정 → 효과 검증).
- `N`·`K`는 자리표시자다. 실제 파일명에 그 글자를 쓰지 않는다.
- 주제는 괄호 안에 짧게. 파일명이 곧 옵시디언 링크 텍스트이므로 README 요약 표에서
  그대로 읽혀야 한다.
- 나중에 실험이 추가되면 **뒤 번호로 붙인다** — 기존 번호를 다시 매기면 다른 문서의
  링크가 깨진다. 순서를 고쳐야 하면 README 요약 표의 행 순서로 조정한다.
- **묶는 기준은 결정 도메인** — 같은 결정을 낳은 측정끼리 한 문서. 방법이 같아도 다른
  결정을 낳았으면 나누고, 방법이 달라도 같은 값을 정했으면 합친다. 판정이 애매하면
  헤딩 깊이를 보조 신호로 쓴다 — 한 REPORT가 H4(`####`) 이상으로 파이면 도메인이
  섞였을 가능성이 크다.
- **기각한 실험·못 한 측정도 독립 문서로 세울 수 있다** — 꼬리 섹션에 두면 묻힌다.
  "왜 안 재도 되게 됐는지"는 잰 것만큼 값어치가 있다.
- 각 문서는 **질문 → 방법 → 결과(표) → 결정** 순서로. 방법은 나중에 같은 측정을 다시
  할 수 있을 만큼 구체적으로 서술한다(표본 수, 조건, 우회한 제약).
- README에는 **요약 표 + 각 문서 링크**만 둔다(템플릿의 `실험 기록` 섹션).

## 첨부 선별 기준

**대전제: 실험 결과는 파일 첨부가 아니라 문서 서술로 남긴다.** 파일을 고르는 일은
그다음이다.

1. **스크립트·코드는 넣지 않는다** — 커밋 여부와 무관하다. 일회성 측정 스크립트도
   보관하지 않고, **무엇을 어떻게 측정했는지를 REPORT에 서술**한다. 재현에 필요한 것은
   코드가 아니라 방법이다. 기법 자체가 재사용 가치가 있으면 교훈 섹션에 요약한다.
2. **자기완결 증빙**(결과 HTML, 스크린샷, 그래프) — 문서로 대체 불가한 시각 자료만.
3. 이미 PR/이슈 트래커에 전문이 있는 것 — 복사하지 않고 README의 links로 충분.
4. **민감 데이터 제외** — 고객·학생 원본 데이터, 원본 URL 목록, 시크릿은 넣지 않는다.
   집계 수치만 문서에 옮긴다.

미커밋 산출물(설계 스펙 등)이 있으면 삭제 전에 알린다. 단 그 목적은 보관이 아니라
**그 안의 결정·실험을 문서로 흡수하는 것**이다 — 흡수했으면 원본은 안 남겨도 된다.

## README 템플릿

```markdown
---
repo: <레포명>
ticket: <티켓번호>
title: <티켓 제목>
period: <YYYY-MM-DD ~ YYYY-MM-DD>
status: <배포 완료 / PR 리뷰 대기 / ...>
tags: [<도메인 태그>, ...]
links:
  ticket: <URL>             # Jira 등 이슈 트래커
  pr: <URL>
  artifact: <URL>          # 있을 때만
---

# <티켓번호> <제목>

## 무엇을 위한 작업인가
문제와 제약. 왜 지금 필요했나.

## 실험 기록 (요약)          # 실측·실험이 있었으면 필수. 없었으면 섹션 생략.
표 한 개: 문서 링크 | 실험 | 핵심 결과 | 그래서 무엇을 결정했나.
상세는 REPORT 문서로 넘긴다. 여기서 수치를 두 번 쓰지 않는다.

## 한 일
번호 목록. 산출물·행동 단위로.

## 규모와 검증              # 있는 것만. 커밋 수·변경량·테스트·리뷰 내역
포트폴리오에서 "이 작업이 얼마만 한 일이었나"에 답하는 수치.

## 결정과 근거
핵심 결정 + 그 근거(비교표 환영). "검토한 대안"이 있으면 여기에.
실험이 근거인 결정은 결과를 다시 늘어놓지 말고 **결정과 REPORT 링크**만.

## 교훈 / 나중의 나에게
이 작업에서만 얻을 수 있는 것: 함정, 진단 요령, 재사용할 판단 기준.
개인 아카이브의 차별 가치는 이 섹션이다 — 성의 있게.

## 첨부
각 파일이 무엇이고 언제 열어볼 만한지 한 줄씩. [[위키링크]] 사용.

## Out-of-Scope / 남긴 것
이번에 안 한 것과 이유. 후속 권장.
```

## 프로세스

1. **실험 목록 만들기 (먼저)** — 이 티켓에서 **무엇을 재고 무엇을 확인했나**를 대화
   맥락에서 먼저 열거한다. 기각한 실험·못 한 측정도 포함. 각 항목의 수치 출처를 확인한다.
   이것이 아카이브의 뼈대다.
2. **수집**: 티켓번호·레포명, PR/티켓/아티팩트 URL, 커밋 범위·변경량, 테스트·리뷰 결과,
   레포 내 보고서 경로, 미커밋 산출물(`git status`).
3. **폴더 생성** → **REPORT 문서 작성**(실험 단위 분할) → **README 작성**(템플릿 순서대로).
   첨부 복사는 자기완결 증빙이 있을 때만, 티켓번호 접두사로 rename.
4. **결과 제시** — 폴더 트리와 README를 보여주고, 사실성 점검(단일 패스 리뷰)
   여부를 묻는다. 수치가 여러 문서에 흩어지면 교차 확인을 권한다.

## Common Mistakes (실측 baseline)

| 실수 | 교정 |
|---|---|
| **실험을 "결정의 근거" 문장 안에만 녹여 씀** | 어떤 실험을 설계했는지가 안 읽힌다. `실험 기록`을 1급 섹션으로 세우고 질문·방법·결과를 분리 |
| **실험 스크립트를 첨부로 복사** | 코드는 안 남긴다. **결과와 방법을 문서로** — 재현에 필요한 건 방법이다 |
| 실험 여러 개를 REPORT 한 파일에 몰아넣음 | 결정 도메인별로 `REPORT N (주제)`로 분할. 기각한 실험도 독립 문서 가능 |
| 첨부 선별을 "소실 위험" 기준으로 판단 | 목적은 보관이 아니라 **포트폴리오 원천 데이터**. 실험·결정 기록이 우선, 파일은 그다음 |
| 첨부를 원래 파일명(`REPORT.md`) 그대로 복사 | 티켓 접두사로 rename — 링크·검색 충돌 |
| 진입점을 `README.md`로 명명 | `<티켓번호> README.md` — 파일명이 곧 링크 키 |
| 폴더명을 티켓번호만으로 (`ABC-135/`) | `<티켓번호> <간단한 설명>` — 폴더만 보고 무슨 작업인지 알게 |
| 교훈 섹션을 형식적으로 한두 줄 | 이 섹션이 아카이브의 존재 이유. 함정·판단 기준을 구체적으로 |
| 원본 데이터·URL 목록까지 복사 | 집계 수치만 문서로. 민감 데이터 제외 |
